## Commands

```bash
# Install dependencies
pip install -r scraper/requirements.txt

# Run the full pipeline locally (~10-15 min for ~25-30k listings)
python scraper/pf_scraper.py      # Step 1: Scrape API → data/raw/
python scraper/cleaner.py          # Step 2: Raw JSON → CSVs in data/latest/
python scraper/comparator.py       # Step 3: Diff vs previous snapshot → data/changes/
python scraper/reporter.py         # Step 4: Generate data/latest_report.json
python scraper/quality_gate.py     # Step 5: Validate quality (exits 1 on failure)
python scripts/load_to_db.py       # Step 6: Diff snapshot into Postgres (needs SUPABASE_DB_URL)
python scripts/update_dashboard.py # Step 7: Regenerate dashboard/data.json

# Quality gate with verbose output
python scraper/quality_gate.py --detailed

# Run tests (cleaner regression against a real archived listing fixture)
pytest tests/
```

## Architecture

**Daily PropertyFinder Bahrain market intelligence pipeline.** Scrapes ~25-30k listings, tracks market changes (new/removed/price-changed) over time, and diffs every daily snapshot into a Supabase Postgres database for long-term analysis / Power BI / AI training.

### Data flow

```
API (__NEXT_DATA__ in Next.js HTML)
  → data/raw/*.json                         (gitignored, large)
  → data/raw_archive/YYYY-MM-DD/*.json.gz   (gzip-compressed, committed)
  → data/latest/*.csv                       (flat 116-column CSVs, committed)
  → data/previous/*.csv                     (yesterday's snapshot, for diffing)
  → data/changes/*.csv                      (cumulative + daily change logs)
  → Supabase Postgres: listings + listing_status + listing_changes + daily_stats  (diff-based, via load_to_db.py)
  → data/latest_report.json                 (pipeline health summary)
  → dashboard/data.json                     (generated by update_dashboard.py)
```

### Scripts

**`scraper/pf_scraper.py`** — Two-phase scraper:
1. Discovery: reads HTML pages via BeautifulSoup to find subcategory URLs (drills down until ≤1,250 listings per URL). **Self-healing splits**: if HTML sub-links cover <80% of a category's total (PF redesigns their markup periodically — it happened June and July 2026), `split_by_price()` recursively bisects the price range via `pf`/`pt` query params using only `__NEXT_DATA__` counts; final fallback scrapes the base URL (1,250 cap) — never zero.
2. Scraping: 4 parallel workers, 0.5s base delay + 0.5s jitter. Reads `__NEXT_DATA__` JSON per page. Deduplicates by `record.get("id")`.

**Hard sanity gate**: after scraping, compares the total against the site's own reported totals (`category["site_total"]`); exits 1 below 60% coverage so a partial scrape can never commit as healthy.

**`scraper/cleaner.py`** — Flattens raw JSON into flat CSVs. Critical detail: the live API wraps each listing as `{listing_type: "property", property: {snake_case fields}}`. The cleaner handles **two formats** (auto-detected):
- **Live format** (from `__NEXT_DATA__`): nested snake_case under `property` — `property.price.value`, `property.location.coordinates.lat`, `property.agent.is_super_agent`, `property.location_tree[...]`
- **Flat format** (test/uploaded data): top-level camelCase keys — `propertyType`, `agentInfo`, etc.

Boolean fields use a `bk(*keys)` helper so Python's `or` chain never drops `False` values. `location_tree` (underscore, NOT `locationTree`) contains `REGION`, `AREA`, and `COMMUNITY` nodes — community nodes are extracted separately; level-1 COMMUNITY is promoted as `area_name` when no AREA node exists.

`COLUMNS` (116 fields) and `PROJECT_COLUMNS` (132 fields) define the exact output schema — the contract with downstream consumers (Supabase, Power BI, n8n). **Do not reorder or remove columns without updating downstream.**

**`scraper/comparator.py`** — Diffs `data/latest/` vs `data/previous/`, writes `data/changes/YYYY-MM-DD.csv` and appends to `data/changes/all_changes.csv`. Rotates latest → previous at the end.

**`scraper/quality_gate.py`** — Validates 5 critical fields (listing_id, price_value, latitude, longitude, title) at 95% threshold, price ranges, row count (min 20,000). Writes `data/latest/quality_report.json`/`.md`. Flags: `--detailed`, `--report-only`.

**`scripts/load_to_db.py`** — Diffs the daily snapshot into Postgres (Supabase project `pf-pipeline`, us-east-1; reads `SUPABASE_DB_URL`, falls back to `NEON_DATABASE_URL`). **Stores changes, not copies**: a full daily copy (~74 MB/day) killed the Neon free tier in 5 days (retired 2026-07-21), so each snapshot is compared to the DB state and only new listings, changed fields and status events are written (~1-2 MB/day) — every day stays reconstructable. Days must load in date order (older-than-latest is refused; already-loaded is a no-op via `load_runs`). Snapshots < 20,000 rows are refused (a partial scrape would fake thousands of "removed" events), and the workflow only loads when the quality gate passed. `IGNORE_CHANGES` (`scraped_at`, `detail_scraped_at`, `lead_value`) change on most listings daily and aren't logged. `safe_cast()` regex-guards all casts — junk like `'none'` (studios' bedrooms_value) becomes NULL. PostGIS `geom` (in the `extensions` schema on Supabase; graceful fallback without PostGIS). RLS enabled on every table with no policies — the Supabase REST API sees nothing until a policy is added on purpose; views are `security_invoker`. Skips silently when no DB URL env var is set.

**`scripts/backfill_db.py`** — Re-cleans every `data/raw_archive/` day newer than the latest loaded day (in a temp dir — `data/` untouched) and loads them in order; partial days are skipped. Run via the `backfill_db.yml` workflow.

**`scraper/reporter.py`** — Writes `data/latest_report.json` with category counts, change summaries, pipeline health.

**`scripts/update_dashboard.py`** — Writes `dashboard/data.json`. Calls the GitHub Actions API (via `GITHUB_TOKEN`, stdlib `urllib` only) to classify red runs as real failures vs cosmetic no-ops (zero jobs = cosmetic). Anomaly warnings only fire if the **most recent** run conclusion is still `failure`. Fill-rate counting treats boolean `"false"` as a filled value, not a gap.

**`scraper/update_handover.py`** — Appends entries to `HANDOVER.md` (called by Actions after each run).

### Secrets (repo → Settings → Secrets → Actions)

- `SUPABASE_DB_URL` — Postgres connection string for the Supabase `pf-pipeline` project (primary)

### Supabase database

Project `pf-pipeline` (AWS us-east-1, free tier 500 MB; recreated Sep 2026 after the original was paused and the load failed silently for 7+ weeks). Loader auto-creates everything on first run:
- `listings` — one row per listing ever seen (`pf_id` PK), all CSV columns typed + PostGIS `geom`; rewritten only when a tracked field changes
- `listing_status` — `pf_id`, `first_seen_date`, `last_seen_date`, `is_active` (the only per-listing write every day)
- `listing_changes` — `(pf_id, change_date, field, old_value, new_value)`; `field = '_status'` holds events (NULL→active new, active→removed, removed→active relisted)
- `daily_stats` — per day × category × area: active/new/removed counts, avg/median price
- `load_runs` — one row per loaded day (audit trail + ordering guard)
- Views: `active_listings`, `price_history`, `market_events` (replaces the old `changes` table / `all_changes.csv` load)

**Storage watch** (measured on a local full backfill, Sep 2026): 103 days (2026-06-09 → 09-23; 07-14/07-15 partial scrapes skipped) = **~350 MB** after compaction (listings 189 MB for 69k listings, listing_changes ~120 MB for 537k rows). Growth ≈ 2 MB/day (≈430 new listings × 2.7 KB + ≈3.9k field changes) → the 500 MB free tier fills around early Dec 2026. Every daily run prints the database size. When it nears the cap: upgrade to Pro (8 GB) or prune old `listing_changes` rows.

### Dashboard

`dashboard/index.html` — static SPA reading `dashboard/data.json`, on GitHub Pages at `bader1919.github.io/pf-pipeline/dashboard/`. Renders pipeline status, category counts, 14-day trend, field fill rates, anomalies, Actions run health.

### Known permanent gaps (not bugs)

Always 0% — PF Bahrain doesn't expose them: `age`, `agent_license_no`, `rera_number`, `rera_authority_name`, `broker_license_number`, `zone_name`, `share_url_translated`, `mortgage_cashback`, `rental_availability_date`

Partial-fill by design: `bedrooms/bathrooms` (~84%, commercial listings omit), `completion_status` (~25%, off-plan only), `community`/`sub_community` (~25%/~3%, master-planned only), `payment_methods` (~40%), `last_refreshed_at` (~0.1%, re-listed only).

### Lessons encoded in this repo (do not regress)

1. **Never trust green checkmarks** — validate content, not process. The gate hard-fails now.
2. **Keep raw data** — the gzip archive turned two data disasters into afternoon fixes.
3. **Test against real data** — `tests/fixtures/live_listing.json` is a real archived listing; the fixture test in CI would have caught every historical cleaner bug.
4. **Expect PF to redesign** — discovery must never depend solely on HTML markup; `__NEXT_DATA__` counts are the stable substrate.

### Raw data archiving / recovery

`data/raw/` is gitignored. Each scrape gzips raw JSON (~85% smaller) to `data/raw_archive/YYYY-MM-DD/` (committed). To re-clean and re-load any past day:

```bash
DATE=2026-06-09
mkdir -p data/raw
for f in data/raw_archive/$DATE/*.json.gz; do
  gzip -d -c "$f" > "data/raw/$(basename $f .gz)"
done
python scraper/cleaner.py
# DB: loads only days newer than the latest loaded one (see backfill_db.py)
```
